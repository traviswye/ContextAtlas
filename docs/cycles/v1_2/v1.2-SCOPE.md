# v1.2-SCOPE.md — Automatic atlas freshness (tiered refresh)

**Status:** Scope-doc drafted 2026-09-24 at v1.2 cycle re-entry
(post-v1.1.3; roughly 2.5 months of inactivity since the prior v1.2
federation draft). Supersedes the 2026-06-09 federation-first v1.2
draft, which is retargeted to
[`../v1_3/v1.3-SCOPE.md`](../v1_3/v1.3-SCOPE.md).

**Why the re-sequence.** Travis locked a use-case pivot on 2026-09-24.
ContextAtlas becomes the **project-brain layer** under a new
workspace command center, built in a separate repo:

```
Workspace command center   (new repo: UI, project/session manager, launcher)
        │
ContextAtlas  +  Session Memory   (new repo: transcript indexer, checkpoints)
        │
CCR (claude-code-router)   (routing, providers, credential pools)
```

A warm-start session is only as good as the atlas it reads. Today
the atlas goes stale silently. Nothing triggers a refresh, and the
running MCP server never re-reads `atlas.json`. The dogfood atlas
was 17 commits behind HEAD at cycle entry. Automatic freshness is
therefore the prerequisite for everything above it, and it is the
smallest change with daily value.

---

## §1 Cycle thesis

v1.2.0 keeps the atlas current **without anyone having to remember
to run anything** and **without becoming a token drain**. Refresh is
split into three cost tiers:

| Tier | What | Cost | Trigger |
|---|---|---|---|
| **0: structural** | LSP symbol inventory, stale-symbol pruning, git signal, SHA diff → pending-source queue | Free (no model calls) | Git hooks: post-commit / post-merge / post-checkout |
| **1: incremental claims** | Re-extract claims for **pending sources only** | Subscription (headless `claude -p` running the `/refresh-atlas` skill); batched + capped | `pre-push` by default; nightly schedule available; manual |
| **2: full / first-time** | Existing `contextatlas index` / `--full` | API | Manual (init recommends API for first extraction; API quality > Skill path per v0.8 65-83% claim-ratio finding) |

The MCP server hot-reloads `atlas.json`, so refreshed state is visible
without restarting sessions. ADR-02's zero-query-time-API-call
invariant is untouched: every tier runs at index time.

## §2 Cycle-entry fresh-read findings (dev, 2026-09-24)

These are verified against source and change the scope.

- **F-1: stale symbols are never pruned.** Stage 0 imports the
  committed atlas (`clearSymbols` + re-insert), and Stage 4 only
  *upserts* the fresh inventory. Stage 5 deletes symbols only for
  deleted **prose** paths (`diff.deleted` comes from the prose walk).
  Symbols from deleted, renamed or moved **source** files, and
  symbols removed from files that still exist, therefore persist in
  `atlas.json` indefinitely. That was tolerable for manual full-ish
  runs but is fatal for a structural-refresh tier whose whole job is
  structural truth. **Fix is Phase 1 and a prerequisite for Tier 0.**
  (`src/extraction/pipeline.ts` Stages 0/4/5;
  `src/storage/symbols.ts` `deleteSymbolsByPath` / `clearSymbols`.)
- **F-2: the shipped CLI `index` extracts ADR/docs claims only.**
  Docstring extraction (`extractDocstringsForFile`, `pipeline.ts`)
  and commit-message extraction (`extractCommitMessagesForRepo`,
  `commit-message-extractor.ts`) are exported library functions.
  They are called only from `scripts/dogfood-extract.mjs` (header
  says "production-grade CLI integration with full three-stream
  support is v0.5+ work", never absorbed) and from benchmarks-repo
  scripts. The `/index-atlas` Skill path does walk all three
  streams. Consequences:
  - Tier 2 "API is higher quality" holds today only for the ADR
    stream via the shipped CLI.
  - Incremental docstring refresh has no CLI-side precedent.

  **Three-stream CLI `index` becomes Phase 2.** Decision point D-1
  (below) covers the cost-default question.
- **F-3: source-SHA tracking is per stream.** Prose files are keyed
  by relPath. Docstrings are keyed per source file
  (`setSourceSha(db, relPath, fileSha)` at `pipeline.ts:877`).
  Commits are keyed `commit:<sha>`. The pending-source queue must
  model all three kinds.

Added 2026-09-24 at Phase 1 entry. F-4 and F-5 were found by the
orchestrator's fresh read and reproduced on real data by the Phase 1
reproducer. F-6 to F-8 were found during Phase 1 implementation.

- **F-4: Stage 5 is not stream-aware (fixed in Phase 1).**
  `diffShas(proseFiles, committedShas)` (`src/extraction/file-walker.ts`)
  marked every `source_shas` key missing from the **prose** walk as
  deleted. That included every docstring key and every commit key.
  Stage 5 then ran `deleteClaimsBySourcePath`, `deleteSymbolsByPath`
  and a `source_shas` delete for each of them.
  - **Affected atlases.** Running CLI `contextatlas index` on any
    three-stream atlas (Skill-built, or built by
    `scripts/dogfood-extract.mjs`) deleted:
    - every docstring claim and every commit claim;
    - the freshly upserted symbols of every docstring-keyed file,
      and with them the ADR claims' links into those files.
  - **The in-code comment was wrong.** The LOCK 2.b comment at Stage
    5 ("commit claims themselves survive") never held for commit
    keys in `source_shas`.
  - **Real-data reproduction** (v0.4 dogfood atlas at 454fcc8, prose
    unchanged, zero API calls; session scratchpad `p1-e2e/`):
    - docstring claims 377 → 0;
    - symbols 768 → 219;
    - `source_shas` 80 → 24;
    - ADR links into the 56 docstring-keyed files 1423 → 0;
    - injected commit claims (3 `commit:<sha>` + 3 bare-sha) 6 → 0.
  - **Silent.** With modern `adr:` prose sources the run exited 0,
    and `validate-extraction` reported "conforms (449 claims across 24
    sources)".
  - **Priority.** Tier 0 (Phase 3) runs Stages 0–5 on every commit,
    so F-4 had to be fixed before it.
- **F-5: commit source keys diverge between paths (record only; Phase
  2).** Both paths set claim `source` to `commit:<sha>`. They differ in
  `source_path` and the `source_shas` key:
  - the CLI commit-message extractor uses `commit:<sha>`
    (`commit-message-extractor.ts`);
  - the Skill uses the bare 40-hex sha (`.claude/skills/index-atlas/
    SKILL.md` Phase B step 3).

  Phase 1 recognizes both forms. Normalizing them belongs to the
  three-stream CLI (Phase 2), which must also migrate existing keys.
- **F-6: `resolve-symbols` leaves dangling claim links (fixed in
  Phase 1).**
  - **Cause.** The Skill-path symbol writer rebuilds `symbols[]`
    wholesale. It also merges each claim's prior `symbol_ids` into the
    new resolution, and it skips claims with no candidates entirely.
  - **Effect.** A link to a symbol whose file was deleted survives, and
    the written `atlas.json` then fails to import with `FOREIGN KEY
    constraint failed`, because `claim_symbols.symbol_id` references
    `symbols.id` with foreign keys ON. That breaks both the MCP server
    and `index`. The wholesale rebuild also drops the symbols of any
    file whose listing failed.
  - **Evidence.** Reproduced by
    `src/extraction/cli-resolve-symbols.test.ts` (real tsserver: resolve,
    delete a file, resolve again) and by a direct `importAtlas` probe.
- **F-7: `claims[].symbol_candidates` does not survive a CLI `index`
  (open; Phase 2/3 input).** The SQLite `claims` table has no column
  for it, so an import → export round trip drops it; this was checked
  with a direct probe. Any CLI `index` run on a Skill-built atlas
  therefore strips the raw candidates that `resolve-symbols` would
  need for a later re-resolution. The hook-driven Tier 0 re-export
  planned for Phase 3 would strip them on every run.
- **F-8: `resolve-symbols` walks without `exclude_pattern` (open;
  Phase 3 decision).** `resolve-symbols` calls `walkSourceFiles`
  without exclude patterns. `index` and `list-extraction-sources` do
  apply them. The two paths therefore produce different symbol sets:
  the Skill path includes test-file symbols, and a CLI `index` (Phase
  1 prune rule 4) removes them again. That churn would show up in
  `atlas.json` diffs once Tier 0 runs automatically. Phase 1 left the
  walk scope unchanged; it changes the Skill path's output, so it
  needs a decision.

### Phase 1: structural correctness (F-1)
- Prune symbols absent from the current inventory after Stage 4, and
  cascade `claim_symbols`. Claims that lose all symbol links are
  reported as **orphaned**. ADR-sourced claims are never deleted by
  pruning, since the ADR still says what it says. Commit claims keep
  the LOCK 2.b orphan-shell retain discipline.
- Report pruned-symbol and orphaned-claim counts in the index summary.

#### Phase 1 outcome (2026-09-24): complete in the working tree, not yet committed

F-1 and F-4 are fixed together; F-6 is fixed as the Skill-path
counterpart. The rules are recorded in the ADR-12 2026-09-24
amendment, which also carries the stage-by-stage prose / docstring /
commit table.
- **Classification** (`src/extraction/source-keys.ts`). Each
  `source_shas` key is classified as prose, docstring or commit.
  - The claim `source` prefix decides. If a key's claims disagree, the
    stream that deletes least wins.
  - Zero-claim keys fall back to shape: a key in the prose walk is
    prose; `commit:` or a bare sha is a commit; an extension of any
    registered adapter makes a docstring key.
  - `src/adapters/registry.test.ts` pins the extension copy to the
    adapters.
- **Stream-aware Stage 5.**
  - prose: deleted iff absent from the prose walk. This now also
    applies under `--full`, which previously never deleted prose keys.
  - docstring: deleted iff the source file is gone.
  - commit: never deleted.
- **Pruning** (`src/extraction/symbol-prune.ts`, Stage 4a).
  - Five rules. Pruned: deleted files, symbols a listed file no longer
    contains, and existing files a configured adapter owns but the walk
    now excludes. Kept as unverified: files whose listing failed, and
    files whose language is not configured.
  - `buildSymbolInventory` now reports `listedPaths` / `failedPaths`.
  - `deleteSymbolsByIds` cascades `claim_symbols`. Claims are never
    deleted; claims left without links are reported as orphaned.
- **Reporting.** New result fields: `symbolsPruned`, `claimsOrphaned`,
  `orphanedClaimsBySource`, `docstringSourcesDeleted`,
  `unverifiedSymbolFiles`.
  - The CLI appends `symbols_pruned`, `claims_orphaned`,
    `docstring_sources_deleted` and `unverified_symbol_files`, plus
    `orphaned_claims_by_source` in `--json`. Existing keys and their
    order are unchanged.
  - `files_deleted` is prose-only again.
- **Export.** Stage 7 re-exports on a prune or a docstring deletion. A
  no-op run leaves `atlas.json` byte-identical.
- **`resolve-symbols`.** It applies the same rules via
  `planSymbolPrune`: prior symbols are kept only for unverified files.
  It also drops `symbol_ids` that match no symbol and reports orphaned
  claims.

### Phase 3: Tier 0 structural refresh + pending queue
- `contextatlas index --structural`: Stages 0–5 + git signal +
  Phase 1 pruning; **skips all model calls**.
  - Changed/added sources across all three streams go into a
    **pending queue** (local cache table; deduplicated by source key,
    so N edits = 1 pending entry) instead of being extracted.
  - Test seam: injected extraction client that throws, which proves
    zero model calls.
- Exports `atlas.json` when structure changed (symbol lines, pruned
  symbols, git signal). Claims are untouched except orphan reporting.
- Pending queue + run log live in gitignored `.contextatlas/local/`.
  This establishes the local-only namespace the v1.3 session overlay
  will reuse.

### Phase 4: MCP server hot reload
- Watch `atlas.json` (`fs.watch` + mtime/content-hash guard,
  debounced). Re-import inside a transaction and swap. In-flight
  queries complete against prior state.
- Log reload events. Survive malformed or partially-written atlases:
  keep the previous state, warn, and retry on the next change.
- **Server wiring (deferred from Phase 0).** Decide whether to replace
  the hand-wired `server.connect(new StdioServerTransport())` in
  `src/index.ts` with SDK v2's `serveStdio(factory)`
  (`@modelcontextprotocol/server/stdio`). `serveStdio` builds a server
  instance per connection from a factory and serves both the 2025-era
  `initialize` handshake and the 2026-07-28 era (`server/discover`).
  Today `server/discover` returns -32601, and a client pinned to
  2026-07-28 cannot negotiate. The factory shape has to fit the
  hot-reload state swap above.

### Phase 5: git hooks + trigger policy
- `contextatlas hooks install | uninstall | status`.
  - Tier 0 runs detached and non-blocking on post-commit / post-merge
    / post-checkout.
  - Tier 1 is queued on `pre-push` (non-blocking; the push is never
    delayed).
- Hooks **chain** with existing hook content (marked block,
  idempotent install, clean uninstall). They respect
  `core.hooksPath`. Shell + `.cmd` shims, no husky (dependency
  minimization).
- **Nightly schedule available, not default:**
  `contextatlas refresh-claims --if-due` is safe for any scheduler.
  Docs ship cron + Windows Task Scheduler recipes. No resident
  daemon.
- `contextatlas init` offers hook installation (opt-in prompt;
  `--yes` accepts).

### Phase 6: Tier 1 incremental claim refresh (subscription)
- `/refresh-atlas` skill, derived from `/index-atlas`. It processes
  **only pending sources**. It reuses the existing Skill-path gates:
  `list-extraction-sources --pending`, `validate-extraction`,
  `resolve-symbols`, `validate-atlas`. It loads the extraction prompt
  via the Read-tool artifact (frozen-prompt load-mechanism rule per
  CLAUDE.md).
- `contextatlas refresh-claims` runner spawns
  `claude -p "/refresh-atlas" --max-turns N` in the repo.
  - Lock file prevents concurrent runs.
  - Drains the queue on success; the overflow beyond caps stays
    pending.
- **Cost controls (hard requirement):**
  - batch, don't run per commit
  - per-run caps (`max_sources_per_run`, `max_turns`)
  - noise filter: vendored/generated/test paths; whitespace-only or
    docstring-unchanged source diffs don't enqueue docstring
    re-extraction
  - usage ledger (`.contextatlas/local/refresh-log.jsonl`)
  - `refresh.auto_claims: off` kill switch (Tier 0 keeps running)
